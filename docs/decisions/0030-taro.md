# 0030. taro: gh for the forge, conventions from merged PRs, cleanup by proof

- **Status:** Accepted; required checks, `behind`, `flaky`, and `cleanup` changed in [0032](0032-taro-fixes.md)
- **Date:** 2026-10-13

## Context

[ADR 0028](0028-propose-ube-and-taro.md) proposed taro, and [docs/taro/design.md](../taro/design.md) described it, with open questions: whether to have `taro land`, whether conventions can be learned from history, and which forges.

## Decision

- **GitHub and GitHub Enterprise through `gh`**: `gh pr view --json`, `gh pr list`, REST for rulesets, branch protection, and Actions, and GraphQL for review threads. The repo comes from `--repo` or the push remote, as `yuzu wait ci` finds it. **GitLab isn't supported yet**, and says so.
- **Auth failures point at `yuzu whoami --verify`.** The design suggested sharing whoami's code; a pointer keeps taro small and the explanation in one place.
- **`ready` blocks on:** a closed or draft PR, conflicts, a failing, pending, or unreported required check, requested changes or a needed approval, unresolved threads, and strong conventions. Behind the base and optional checks failing only warn.
- **Required checks** come from rulesets and branch protection. Both return 403 on a free private repo, so when neither can be read, every check counts, and the output says why.
- **Conventions come from the last 30 merged PRs**: a changelog entry, an ADR, a Conventional Commits title. They need at least 10 merged PRs, block at 90%, and warn at 60%, with the counts shown, like recipe's thresholds.
- **`flaky`** reads up to 500 Actions runs in the window. A flake is a run that passed on a rerun after a failed attempt (named by job, from the attempts' job lists), or a workflow that both failed and passed on one commit. Failures that never passed aren't counted.
- **`owners` and `cleanup` are local**: CODEOWNERS with gitignore-style patterns (last match wins) and `git log` authors; and branch proofs by ancestry, `git cherry` (every patch present), a matching squash patch id, or identical content for every file the branch changed. Unproved branches are kept, with the reason.
- **`cleanup --delete` asks**; without a terminal it needs `--yes`. **No `taro land`**: taro reports, merging stays with the user, and the skill says not to merge or delete unasked.
- No new dependencies. taro is 1,629 KB.

## Results (2026-10-13)

- On this repo: `taro ready 6` passed, noting unreadable required checks and too few merged PRs for conventions; `taro flaky` found none in 18 runs; `taro cleanup --remote` kept `feat/ube` and the Dependabot branch with their commits named.
- Fixtures merged by merge commit, rebase, and squash are each proved, an open branch and a half cherry-picked one are kept, and `--delete --yes` deletes exactly the proved three. Breaking the rebase or squash proof, or accepting a half-landed branch, fails a test.
- 8 integration tests run the binary against real repos and a stub `gh`.

## Consequences

- The design's bars need team repos (ready's 95% agreement over 30 PRs, flaky against known flakes), which this repo and Anchor aren't. They're unmeasured.
- Squash detection compares one patch id, so a squash merge that was edited while merging isn't proved, and is kept.

## Alternatives considered

- **`taro land`:** convenient, but it crosses from reporting into acting on shared state.
- **GitHub's API through an HTTP client in Rust:** no `gh` dependency, but auth, Enterprise hosts, and pagination are what `gh` already does well, and users already have it.
